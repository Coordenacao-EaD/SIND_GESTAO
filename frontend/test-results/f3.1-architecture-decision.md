# ADR F3.1A2 — Arquitetura do backend e persistência

- **Status:** Proposta para aprovação
- **Data:** 2026-08-11
- **Decisão precedente:** `f3.1-architecture-audit.md`
- **Escopo:** decisão arquitetural; nenhuma implementação autorizada
- **Responsáveis pela aprovação:** arquitetura, segurança e responsável técnico do produto

## Contexto

A F2 representa em memória os fluxos editoriais da Home. A F3 deverá persistir banners, contatos, configurações/links sociais, revisões e versões consolidadas sem enfraquecer as regras já aprovadas. A auditoria F3.1A confirmou que não existe infraestrutura anterior a preservar: não há backend, banco, driver, ORM/query builder, migration runner, users, PK/FK persistentes, banco de testes ou CI de migrations.

Uma nova verificação da raiz encontrou somente `.git`, `.claude`, `frontend`, `protótipo` e `.gitignore`. Portanto, continua inexistente uma infraestrutura backend concorrente com esta proposta.

## Problema

É necessário escolher uma arquitetura única antes da F3.1B. Ela deve representar explicitamente no banco, e não apenas na aplicação:

- uma única linha `published` em cada agregado editorial;
- uma única versão consolidada `is_current = true`;
- uma única revisão `pending` por conteúdo;
- PKs, FKs, CHECKs e índices nomeados;
- transações, concorrência, migrations `up/down` e rollback testável;
- snapshot JSON imutável;
- segregação de atores e histórico preservado;
- testes contra a mesma engine real usada em produção.

## Restrições

- Não criar backend, banco, Docker, migrations, tabelas, API ou autenticação nesta decisão.
- Não alterar frontend, Home pública, mocks ou protótipo.
- Não criar usuário falso nem credenciais de produção.
- Não usar SQLite ou NoSQL como banco de produção.
- Não depender exclusivamente de validação da aplicação para CT-HOM-010.
- Não instalar dependências nesta etapa.
- Separar responsabilidades de F3.1, F3.2 e F3.3.

## Decisão resumida

Adotar, após aprovação, um **monólito modular em Node.js LTS + TypeScript**, com **Fastify** como framework HTTP futuro, **PostgreSQL 18** como banco relacional, **SQL parametrizado diretamente com `pg`**, e **migrations SQL puras gerenciadas pelo dbmate**. O backend ficará em `backend/`, separado do frontend.

As entidades usarão **UUID como PK**, gerado pelo PostgreSQL por padrão e aceitando UUID explícito em testes. Datas serão `timestamptz` em UTC. Snapshots serão `jsonb`. Reviews manterão o contrato `content_type/content_id`, mas obterão integridade real por três FKs opcionais, CHECK de exatamente uma e `content_id` gerado da FK escolhida.

A F3.1 criará uma tabela mínima `app_users`, sem senha, sessão, role ou usuário seed de produção. Ela será apenas o identificador interno estável referenciado pelas FKs de auditoria. A F3.3 adicionará autenticação e o vínculo entre identidade externa e `app_users`, sem trocar as PKs da Home.

Testes de banco usarão **PostgreSQL efêmero via Testcontainers**, exigindo Docker ou runtime de containers compatível. Desenvolvimento interativo poderá usar Compose com instância local persistente, mas o teste automatizado nunca reutilizará esse volume.

## 1. Arquitetura do backend

### Decisão

- Runtime: Node.js 24 LTS.
- Linguagem: TypeScript em modo estrito, módulos ESM.
- Forma: monólito modular, uma aplicação e um banco; sem microserviços.
- HTTP futuro: Fastify.
- Validação HTTP futura: JSON Schema do Fastify na borda; regras de domínio em services; constraints no banco.
- Camadas: routes/controllers → services/use cases → repositories → `pg`/PostgreSQL.
- Módulos iniciais: `identity` e `home`; infraestrutura compartilhada em `config` e `database`.
- Testes: Vitest para unitários e integração; Testcontainers para PostgreSQL real.

Node 24 compartilha linguagem, compilador, ESM, npm e práticas de teste com o frontend sem acoplar seus manifests. A política oficial do Node recomenda produção apenas em linhas Active/Maintenance LTS; a linha 24 está em LTS na data desta decisão. A versão patch deverá ser a mais recente suportada e validada no início da implementação, nunca `latest` sem pin. [Node.js Releases](https://nodejs.org/en/about/previous-releases)

Fastify fornece lifecycle enxuto, plugins encapsulados e validação/serialização por JSON Schema. O framework não acessará o banco diretamente nos handlers; chamadas assíncronas de domínio ficam após a validação estrutural. [Fastify: Validation and Serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

### Organização e fronteiras

- Routes/controllers apenas convertem HTTP em comandos e respostas.
- Services controlam workflow, autorização, hash, lock e transação.
- Repositories contêm SQL e mapeamento de linhas, sem regra HTTP.
- A conexão/transação entra no repository por contexto explícito.
- O frontend continuará independente; integração HTTP pertence à F3.3.
- Nenhuma entidade do frontend será importada diretamente pelo backend. Contratos compartilháveis só poderão surgir depois, em pacote próprio e com versionamento deliberado.

## 2. Alternativas de backend consideradas

| Alternativa | Vantagens | Riscos/complexidade | Impacto e adequação à F3 | Decisão |
|---|---|---|---|---|
| Node.js + TypeScript + Fastify | mesmo ecossistema; baixo overhead; JSON Schema; plugins; boa testabilidade | exige disciplina arquitetural, pois não impõe camadas | integração futura simples; adequado ao domínio e sem excesso de framework | **escolhida** |
| Node.js + TypeScript + NestJS | módulos/DI/opiniões fortes; ecossistema maduro | bootstrap e abstrações maiores; fácil introduzir ORM/decorators desnecessários | útil em equipe grande, mas custo atual não se justifica para um módulo inicial | rejeitada |
| Node.js + TypeScript + Express | muito maduro e conhecido; mínimo | validação, serialização, lifecycle e estrutura dependem de composição manual | viável, porém mais decisões e middleware para alcançar o mesmo baseline | rejeitada |
| ASP.NET Core/C# ou Java/Spring | stacks maduras, tipadas e fortes para transações | nova linguagem, build, package manager e operação sem evidência institucional | tecnicamente adequadas, mas ampliam onboarding e CI sem benefício comprovado | rejeitadas |
| microserviços | isolamento independente | rede, observabilidade, consistência distribuída e operação excessivas | seis tabelas fortemente relacionadas pedem transação local | rejeitada |

## 3. Banco de dados

### Decisão: PostgreSQL 18

PostgreSQL 18 é a major estável atual e recebe suporte oficial até 2030; a implementação deverá confirmar a minor corrente, compatibilidade das ferramentas e fixar major + minor/digest da imagem. O projeto deve atualizar minors de segurança da mesma major. [Política de versões do PostgreSQL](https://www.postgresql.org/support/versioning/)

Adequação específica:

- índices únicos parciais representam diretamente as cinco invariantes condicionais;
- CHECKs e FKs são nativos e geram erros identificáveis;
- transações, locks de linha e níveis de isolamento sustentam publish/restore concorrentes;
- `jsonb` armazena o snapshot validado;
- `timestamptz` armazena instantes sem ambiguidade;
- DDL transacional permite `up/down` atômicos na maioria das migrations;
- containers oficiais viabilizam ambiente idêntico em desenvolvimento e CI.

PostgreSQL documenta que um índice parcial pode ser UNIQUE e, assim, impor unicidade somente às linhas que satisfazem o predicado. [PostgreSQL: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html)

### Invariantes condicionais

Estratégia física a implementar na F3.1B, com nomes definitivos na migration:

| Invariante | Índice único parcial recomendado |
|---|---|
| um banner published | coluna `status`, `WHERE status = 'published'` |
| um contato published | coluna `status`, `WHERE status = 'published'` |
| uma configuração social published | coluna `status`, `WHERE status = 'published'` |
| uma versão atual | coluna `is_current`, `WHERE is_current` |
| uma review pending por conteúdo | `(content_type, content_id)`, `WHERE decision = 'pending'` |

A transação arquiva a linha vigente antes de publicar a nova. Se duas transações concorrerem, a constraint decide; o service traduz o código/nome da violação em conflito. A pré-consulta é apenas UX, nunca garantia.

### Alternativas de banco

| Banco | Pontos favoráveis | Limitações para esta F3 | Decisão |
|---|---|---|---|
| PostgreSQL | índice parcial nativo; `jsonb`; `timestamptz`; locks e DDL transacional | operação e tuning precisam ser definidos | **escolhido** |
| SQL Server | índices filtrados, JSON por funções, transações maduras | ecossistema/driver/operação adicionais e JSON não é tipo equivalente a `jsonb` | rejeitado |
| MySQL/MariaDB | maduros, amplamente hospedados | unicidade condicional exige coluna gerada/desenho indireto; sem vantagem comprovada | rejeitados |
| SQLite | simples e rápido localmente | concorrência, tipos e paridade de produção inadequados ao objetivo | rejeitado para produção e teste de integração |

## 4. Acesso ao banco

### Decisão: SQL parametrizado direto com `pg`

Repositories usarão consultas SQL explícitas com placeholders `$1`, `$2` etc. O driver `pg` envia parâmetros separadamente e oferece pool. Transações usarão um único client adquirido do pool, com `BEGIN`, `COMMIT`, `ROLLBACK` e liberação em `finally`. [node-postgres: queries parametrizadas](https://node-postgres.com/features/queries), [pooling](https://node-postgres.com/features/pooling), [transações](https://node-postgres.com/features/transactions)

Regras:

- valores externos nunca serão concatenados em SQL;
- nomes de tabela/coluna não serão dinâmicos a partir de input;
- queries receberão timeout e `application_name`;
- locks serão explícitos (`SELECT ... FOR UPDATE`) somente dentro de transação;
- helpers internos padronizarão transação e tradução de erros, sem virar ORM;
- SQL crítico terá teste de integração real.

### Alternativas de acesso

| Abordagem | Vantagens | Riscos | Decisão |
|---|---|---|---|
| `pg` + SQL explícito | invariantes e locks visíveis; previsibilidade; baixa dependência | mapeamento e tipagem de rows exigem disciplina | **escolhida** |
| query builder (Kysely/Knex) | composição e alguma tipagem | DDL/índices parciais ainda exigem SQL; camada adicional | rejeitado no início; reavaliar se repetição real justificar |
| ORM (Prisma/TypeORM/Sequelize) | produtividade CRUD/relations | pode esconder transações/SQL e não elimina migrations SQL específicas | rejeitado |

## 5. Migrations

### Decisão: SQL puro com dbmate

O dbmate usa arquivos SQL versionados por timestamp, blocos `-- migrate:up` e `-- migrate:down`, tabela de histórico, comandos `up/down/status` e transações por padrão. [dbmate: documentação oficial](https://github.com/amacneil/dbmate)

- Ferramenta: `dbmate` como devDependency do backend.
- Diretório: `backend/db/migrations/`.
- Schema dump auditável: `backend/db/schema.sql`.
- Nome: `YYYYMMDDHHMMSS_descricao_em_snake_case.sql`, timestamp UTC de 14 dígitos.
- Up/down: no mesmo arquivo e ambos obrigatórios.
- Ordem: versão numérica do nome; nunca renumerar migration aplicada.
- Transação: padrão `true`; exceção somente documentada quando PostgreSQL exigir DDL não transacional.
- Histórico: tabela `schema_migrations` do runner.

Scripts futuros do `backend/package.json`:

```json
{
  "scripts": {
    "db:new": "dbmate --migrations-dir db/migrations --schema-file db/schema.sql new",
    "db:up": "dbmate --migrations-dir db/migrations --schema-file db/schema.sql up",
    "db:down": "dbmate --migrations-dir db/migrations --schema-file db/schema.sql down",
    "db:status": "dbmate --migrations-dir db/migrations --schema-file db/schema.sql status"
  }
}
```

Comandos futuros, após o bootstrap autorizado:

```powershell
Set-Location C:\Users\gabrielalmeida\Desktop\sind_gestao\backend
npm run db:status
npm run db:up
npm run db:down
npm run db:up
npm run test:db
```

Nenhum desses comandos existe ou foi executado nesta tarefa.

## 6. Identificadores

### Decisão: UUID

- PK principal de `app_users` e das seis tabelas da Home: PostgreSQL `uuid`.
- Default de banco: função UUID aleatória nativa suportada pela versão fixada.
- A aplicação normalmente omite a PK no insert; o banco gera.
- Testes podem fornecer UUIDs fixos e válidos para legibilidade/determinismo.
- Todas as FKs usam exatamente `uuid`.
- UUID é serializado como string nas bordas e não revela cardinalidade/sequência em APIs futuras.

BIGINT é mais curto e amigável em consulta manual, mas acopla geração a uma sequência central e expõe enumeração. O domínio já usa identificadores textuais opacos no frontend, e a futura integração de identidade favorece um ID interno não sequencial. Exceções: `version_number`, `cycle_number`, `display_order` e versão de migration são números de negócio/ordenação, não PKs.

## 7. Identidade e tabela de usuários

### Decisão: `app_users` mínima como âncora interna

A F3.1 criará a estrutura vazia `app_users`, sem autenticação e sem seed de produção. Campos mínimos:

- `id uuid primary key`;
- `status` com estados internos mínimos aprovados (`active`, `inactive`);
- `created_at timestamptz`;
- `updated_at timestamptz`.

Não entram senha, hash de senha, token, sessão, email obrigatório, perfil, role, capability, provider ou subject externo. Testes de migration inserem usuários efêmeros somente no banco isolado e fazem cleanup pela destruição do container.

Todas as colunas `created_by`, `updated_by`, `submitted_by`, `reviewed_by`, `invalidated_by` e `published_by` terão FK para `app_users(id)`, com `ON DELETE RESTRICT` e PK imutável. Usuários serão inativados, não fisicamente apagados enquanto houver histórico.

Na F3.3, autenticação real resolve a identidade externa para um `app_users.id`. Recomenda-se uma tabela separada `user_external_identities` com chave única `(provider, subject)` e FK para `app_users`; perfis/roles/capabilities também ficam separados. Assim, trocar ou adicionar provedor não altera nenhuma FK editorial.

### Alternativas avaliadas

| Opção | Avaliação | Decisão |
|---|---|---|
| tabela mínima interna agora | preserva FKs e desacopla autenticação; não requer credenciais | **escolhida** |
| aguardar toda a autenticação | evita tabela inicial, mas bloqueia F3.1 e acopla persistência ao provedor futuro | rejeitada |
| actor ID sem FK temporária | permite avanço rápido, mas aceita órfãos e exige migration corretiva/destrutiva | rejeitada |
| usar diretamente PK de provedor externo | simples para um provedor, mas cria lock-in e tipo externo no domínio | rejeitada |

## 8. Timestamps

### Decisão

- Tipo: `timestamptz`, com precisão compatível com a borda JavaScript (preferência `timestamptz(3)`).
- Armazenamento: instante em UTC; sessão/conexão de aplicação configurada para UTC.
- Saída HTTP futura: ISO 8601/RFC 3339 com `Z`; localização `America/Cuiaba` somente na apresentação.
- Nomes: snake_case (`created_at`, `submitted_at`, `reviewed_at`, `published_at`, `archived_at`, `invalidated_at`).
- Geração: banco, usando `CURRENT_TIMESTAMP` no statement/transação.
- `created_at`: `NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- `updated_at`: repository atualiza explicitamente com `CURRENT_TIMESTAMP`; não usar trigger genérico oculto.
- Timestamps de eventos: definidos no mesmo SQL que efetiva a transição; nulos até o evento.

PostgreSQL converte `timestamp with time zone` para UTC internamente e apresenta conforme a timezone da sessão, evitando que um horário brasileiro sem offset se torne ambíguo. [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html)

## 9. Snapshot JSON

### Decisão

- `site_home_versions.snapshot_json`: `jsonb NOT NULL`.
- Conteúdo: envelope versionado, por exemplo `schema_version`, banner, contacts e social configuration; não substitui FKs/tabelas normalizadas.
- Serialização: service F3.2 monta objeto canônico a partir das linhas publicadas e persiste como parâmetro; hash usa canonicalização definida e testada, não a ordenação textual retornada pelo banco.
- Consulta: leitura do snapshot inteiro por PK/versão; não criar GIN inicialmente. Índice interno só após consulta real e evidência de plano.
- Testes: validade, round-trip sem perda semântica, `schema_version`, hash determinístico e rejeição de mutação.
- Imutabilidade: trigger permite na linha histórica somente a transição necessária de `is_current: true → false`; referências, snapshot, summary, autoria e publicação permanecem imutáveis. Repository é append-only e o papel runtime recebe somente permissões necessárias.

PostgreSQL oferece `json` e `jsonb`; `jsonb` é a escolha por validação binária, operadores e possibilidade futura de indexação, sem tratá-lo como modelo primário. [PostgreSQL: JSON Types](https://www.postgresql.org/docs/current/datatype-json.html)

## 10. Reviews polimórficas

### Decisão: três FKs + coluna pública gerada

`site_home_reviews` terá:

- `content_type` com CHECK em `banner`, `contacts`, `social_configuration`;
- `banner_id uuid null` FK;
- `contacts_id uuid null` FK;
- `social_configuration_id uuid null` FK;
- CHECK `num_nonnulls(...) = 1`;
- CHECK ligando `content_type` à única FK não nula;
- `content_id uuid generated always as (coalesce(...)) stored`;
- UNIQUE `(content_type, content_id, cycle_number)`;
- unique parcial `(content_type, content_id) WHERE decision = 'pending'`.

Isso mantém a forma conceitual F2 (`contentType/contentId`) nos repositories/APIs e, simultaneamente, fornece FKs reais. Restore e histórico localizam diretamente o agregado correto. O custo de três colunas e CHECKs é aceito para apenas três tipos estáveis.

| Alternativa | Integridade | Complexidade/compatibilidade | Decisão |
|---|---|---|---|
| service/transaction sem FK | insuficiente contra órfãos e operações externas | contrato simples, integridade fraca | rejeitada |
| três FKs + CHECK | FKs reais e sem nova entidade | mais colunas/índices; mapeamento simples | **escolhida** |
| supertype editorial | forte e extensível | adiciona sétima entidade/lifecycle sem necessidade atual | rejeitada por agora |
| trigger para FK dinâmica | possível, porém específico e mais difícil de manter/rollback | esconde integridade em código procedural | rejeitada |

## 11. Banco de teste e Docker

### Decisão: Testcontainers + Docker

- Testes de integração iniciam um PostgreSQL 18 efêmero com `@testcontainers/postgresql`.
- Tag/digest deve ser igual ao major/minor aprovado para produção.
- Porta do host será aleatória; banco/usuário/senha serão exclusivos do container.
- O teste passa a URI temporária ao dbmate, executa `up → asserts → down → asserts → up` e encerra o container.
- Sem volume e sem compartilhamento entre suítes; paralelismo somente com containers/bancos independentes.
- CI futura fornece Docker/container runtime e cache de imagem, não banco persistente.

O módulo oficial de Testcontainers para Node expõe host, porta, database, usuário, senha e URI de uma instância PostgreSQL iniciada pelo teste. [Testcontainers PostgreSQL](https://node.testcontainers.org/modules/postgresql/)

Docker (ou runtime compatível oficialmente suportado por Testcontainers) será requisito para F3.1B4 e testes locais de banco. Para desenvolvimento manual, um futuro `backend/compose.yaml` terá conceitualmente:

| Item | Definição futura |
|---|---|
| serviço | `postgres` |
| imagem | `postgres:18.<minor>` fixada e, em CI, preferencialmente por digest |
| porta | `${POSTGRES_PORT:-5432}:5432`; Testcontainers usa porta aleatória |
| volume | nomeado somente para desenvolvimento; nenhum em teste |
| healthcheck | `pg_isready` com usuário/database de desenvolvimento |
| variáveis | valores não secretos vindos do `.env` local; placeholders no `.env.example` |

Banco local dedicado e schema temporário foram rejeitados como padrão porque deixam estado residual e reduzem isolamento. Compose sozinho é útil para desenvolvimento, mas Testcontainers é superior para lifecycle automatizado da suíte.

## 12. Segredos e configuração

- `DATABASE_URL`: conexão do papel runtime de menor privilégio.
- `DATABASE_MIGRATION_URL`: conexão separada para DDL/migrations; nunca usada pela aplicação em execução.
- `.env`: local, ignorado pelo Git, permissões restritas, nunca logado.
- `.env.example`: versionado, apenas nomes e valores obviamente fictícios.
- Testes: URI criada pelo Testcontainers em memória; não reutiliza credenciais locais.
- Produção: variáveis injetadas por secret manager/orquestrador, não arquivo versionado.
- Startup valida presença/formato sem imprimir senha ou URL completa.
- Logs podem registrar host lógico/ambiente somente se sanitizados.

## 14. Separação F3.1 / F3.2 / F3.3

| Fase | Inclui | Exclui |
|---|---|---|
| F3.1 | bootstrap mínimo; configuração de DB; dbmate; `app_users`; seis tabelas; constraints/índices/triggers estritamente estruturais; Testcontainers; CT-HOM-010; up/down/up | repositories funcionais, API, autenticação, workflow real |
| F3.2 | `pg` pool; repositories; transações; locks; hash/canonicalização; publish; persistência; restore; testes de integração | controllers/API e autenticação HTTP |
| F3.3 | services de workflow; Fastify; controllers/routes; autenticação/autorização; vínculo externo de identidade; auditoria operacional; contrato administrativo HTTP | mudança das invariantes físicas já aprovadas sem nova migration/ADR |

O bootstrap F3.1 pode declarar a dependência `pg` para testes e preparação, mas não implementa repository de negócio. Fastify só precisa ser instalado quando houver uso em F3.3; a arquitetura é decidida agora, a dependência não é antecipada.

| `vitest` | testes unitários/integração | dev | alinhamento com frontend e suporte TypeScript | sim, F3.1 |
| `oxlint` | lint | dev | alinhamento com baseline existente | sim, bootstrap |
| `tsx` | execução TypeScript em desenvolvimento/scripts | dev | evita build manual no ciclo local | sim quando primeiro entrypoint TS executável existir |

Não são propostos ORM, query builder, `dotenv`, biblioteca de UUID nem segundo test runner. Node/dbmate cobrem arquivo de ambiente local; PostgreSQL gera UUID; JSON Schema/Fastify cobrem a borda futura.

## 16. Naming e políticas estruturais

- Tabelas/colunas: `snake_case`, plural para tabelas.
- PK: `pk_<table>`; FK: `fk_<child>__<parent>__<column>`.
- CHECK: `ck_<table>__<rule>`; UNIQUE constraint: `uq_<table>__<columns>`.
- Índice comum: `ix_<table>__<columns>`; unique parcial: `ux_<table>__<invariant>`.
- `ON DELETE RESTRICT` para conteúdo, users, reviews e versions; histórico usa arquivamento/inativação.
- `ON UPDATE RESTRICT`; PKs não mudam.
- Links sociais pertencem à configuração; remoção física somente de draft não referenciado, em operação explícita. Nada de cascade sobre histórico publicado.

## 17. Segurança

- Somente statements parametrizados para valores.
- Identificadores SQL são constantes no código/migration, nunca input do usuário.
- Papel runtime sem CREATE/ALTER/DROP e sem acesso à tabela de migration.
- Papel de migration separado, usado apenas em deploy/controlado.
- TLS com verificação de certificado fora do ambiente local descartável.
- Pool único por processo, máximo dimensionado com limite do servidor; timeouts de conexão, checkout, statement e idle transaction.
- Transação sempre em um único client e rollback em `catch`.
- Logs estruturados com parâmetros sensíveis redigidos; sem SQL completo quando contiver dados pessoais.
- Erros públicos não expõem constraint/SQL; camada interna mapeia nomes estáveis para conflitos.
- `.env`, URLs e credenciais nunca entram no Git.
- Migração/rollback somente em banco alvo explicitamente identificado; scripts devem recusar ambiente de produção para testes destrutivos.

## 18. Consequências

### Positivas

- CT-HOM-010 é garantido pela engine, inclusive sob concorrência.
- SQL, locks e transações ficam visíveis e testáveis.
- Linguagem/ecossistema são familiares ao projeto sem acoplamento de deploy.
- PostgreSQL fornece `jsonb`, `timestamptz`, FKs e partial unique indexes nativos.
- Identidade interna evita FK temporária e lock-in de provedor.
- Migrations SQL são auditáveis e reversíveis.
- Testcontainers reduz diferença entre laptop e CI.

### Custos

- Docker/runtime de containers torna-se pré-requisito dos testes de banco.
- SQL explícito demanda disciplina de tipagem/mapeamento.
- Três FKs de review geram mais colunas e índices.
- A equipe deve operar PostgreSQL, pool, migrations e upgrades.
- `app_users` exige uma migration mínima antes das entidades editoriais.

## 19. Riscos e mitigação

| Risco | Mitigação |
|---|---|
| ADR aprovada, mas versões incompatíveis na implementação | confirmar matriz Node/Fastify/pg/dbmate/Testcontainers e fixar lockfile/imagem antes do bootstrap |
| Docker indisponível em estação/CI | gate explícito de pré-requisito e documentação de runtime compatível |
| migration down destrutiva fora de teste | credenciais/URLs separadas, confirmação de ambiente e execução automatizada apenas em DB efêmero |
| UUID/default variar entre versões | teste da função na major fixada e fixtures explícitas |
| `app_users` virar autenticação improvisada | proibir credenciais/roles na F3.1 e reservar vínculo externo à F3.3 |
| inconsistência entre `content_type` e FK | CHECK de exatamente uma + CHECK de coerência + testes negativos |
| snapshot ser alterado | trigger estrutural, permissões e repository append-only |
| lock/transação incorretos em publish | helper transacional, mesmo client e testes concorrentes na F3.2 |
| pool esgotado | limites/timeouts, release em `finally`, métricas futuras |
| minor PostgreSQL/Node ficar desatualizada | política de patch/minor suportada e revisão periódica |

## 20. Decisões adiadas

Não bloqueiam a aprovação desta arquitetura, mas não podem ser inventadas na F3.1:

- provedor/protocolo de autenticação da F3.3 e modelo de roles/capabilities;
- contrato HTTP, versionamento e política CORS;
- hospedagem/serviço gerenciado de PostgreSQL em produção;
- plataforma de CI/CD e secret manager;
- observabilidade, tracing e retenção de logs;
- tamanho final do pool, SLA e estratégia de backup/restore;
- eventual read replica/cache;
- índices JSONB, somente se consultas reais justificarem;
- política de retenção de histórico e LGPD além de `RESTRICT`/inativação;
- compartilhamento formal de schemas entre frontend e backend.

## 21. Matriz final

| Item | Decisão recomendada | Alternativas rejeitadas | Motivo principal |
|---|---|---|---|
| runtime | Node.js 24 LTS | runtimes EOL/current não LTS; .NET/Java | suporte e ecossistema atual |
| linguagem | TypeScript strict/ESM | JavaScript sem tipos; nova linguagem | consistência e contratos |
| framework | Fastify | NestJS, Express | validação/lifecycle com baixo overhead |
| arquitetura | monólito modular | microserviços | transações locais e escopo atual |
| banco | PostgreSQL 18 | SQL Server, MySQL/MariaDB, SQLite | partial unique, JSONB, timestamptz |
| driver | `pg` | drivers indiretos de ORM | parâmetros, pool e controle explícito |
| acesso | SQL direto | ORM/query builder | invariantes/locks visíveis |
| migration runner | dbmate + SQL puro | migrations de ORM/programáticas | up/down/status e DDL auditável |
| PK | UUID | BIGINT | identidade opaca e integração futura |
| usuários | `app_users` mínima sem credenciais | esperar auth; actor sem FK; PK externa | FKs agora sem lock-in/fake auth |
| timestamp | `timestamptz(3)`, UTC, gerado no banco | timestamp sem timezone; relógio do cliente | instantes não ambíguos |
| JSON | `jsonb` | `json`, TEXT | validação/operadores e evolução |
| reviews | 3 FKs + CHECK + `content_id` gerado | polimorfismo sem FK; supertype; trigger | integridade real e contrato F2 |
| test DB | Testcontainers PostgreSQL | SQLite, banco compartilhado, só Compose | mesma engine e isolamento |
| Docker | obrigatório para testes F3 | instalação de DB institucional/local compartilhado | reprodutibilidade e cleanup |
| configuração | URLs runtime/migration separadas | credenciais em código; uma conta privilegiada | menor privilégio |
| diretório | `backend/` com `db/`, `src/`, `test/` | misturar em frontend; `server/` não existente | separação clara e convenção definida |

Gate: CT-HOM-010 100%, rollback/reaplicação, zero banco institucional e zero regressão frontend.
